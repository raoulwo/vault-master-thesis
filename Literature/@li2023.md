# Seamless Cross-Edge Service Migration for Real-Time Rendering Applications

## TLDR

%% One-sentence summary of the core/claim contribution. %%

The paper proposes *Cloud-assisted Service Migration (CSM)* which leverages cloud-edge collaboration to achieve seamless service migration for real-time rendering applications.

%% Notes about the paper. %%

## Introduction

- Problem: Real-time rendering apps are limited by weak computing capability of equipment
- Solution: Move rendering to cloud and stream the rendered images to user equipment (UE)
	- Problem: Long distances between UE and cloud brings extra high latency
	- Solution: Edge-rendering for low latency rendering at network edge
- Real-time rendering apps rely on real-time streaming protocols:
	- e.g. RTSP, RTMP
- Low-latency requirements limit the coverage of edge-cloud networks
- Some streaming systems don't buffer on UE to reduce latency even further
	- Makes streaming more vulnerable to latency increases
- *Follow me cloud* is proposed that uses service migration to follow mobile users
	- However, migration is costly and introduces downtime which negatively affects UX
- **Reducing downtime to $\le 15$ms is important to prevent unpleasant UX**
- Two approaches for live migration: VM and container
	- Not ideal for real-time apps since downtime to high
	- Existing methods such as pre-copy and post-copy don't meet 15ms requirements
- Can migrate containers as processes using [[Checkpoint;Restore in Userspace (CRIU)]]
	- **Doesn't support checkpoint of graphical applications**
	- Real-world scenarios all use VMs for migration of graphical apps

Proposal of cloud-assisted service migration (CSM) architecture:

- Copying all the state is too costly, instead recover state from prior data flow
- Clodu-assisted dual rendering instead of peer-to-peer state copy
- 2 key challenges
	1. How to achieve switch of session and 5G user plane session with downtime limitation?
		- How do we prevent unnecessary downtime?
		- Solution: UE-centric session management mechanism
	2. How to maintain continuity of UE screen during session switching?
		- Migrating video streams of source server to destination server can lead to UE receiving differing frames -> noticeable by user
		- Solution: Introduce smooth switching mechanism using Structural Similarity (SSIM)

## Contributions

- Show dat transference resulting from dirty page retransmission-induced repeated memory data copy is performance bottleneck
- Propose CSM, uses cloud-assisted dual rendering
	- Potentially first work to consider not only computation state transference
- Develop UE-centric session management and smooth switching mechanism
- Implement proposed architecture based on 5G core network

## Background and Motivation

### Understanding Real-Time Applications

- Real-time apps are delay-sensitive and computation-intensive
- Example for real-time apps are multiplayer games
- Three parts of real-time apps:
	- Global logical module
		- Main logic
		- Provides virtual world
	- Rendering module
		- 2D/3D video
	- Front-end module
		- decodes and displays video
		- collects user input and sends it
- Real-time rendering architectures:
	- Local rendering
	- Cloud rendering
	- Edge rendering

### Understanding Service Migration Downtime

- Service migration includes two processes:
	- Network hand-off
	- Computation state migration

### Case Study

- Conducted to evaluate performance off current VM and container migration techniques
- Shows that VM migration time and downtime are way too high for 15ms requirement
- CRIU checkpointing for containers is largest contributor to downtime

## System Design

### Overview

- Instead of p2p memory state copy, dual rendering method
- Make use of global state in cloud server to restore rendering module state at destination
	- Bypasses direct memory copy
	- Works in asynchronous mode
	- Network switch embedded in whole workflow, adapted to 5G network architecture
- Dual rendering mechanism brings challenges in state synchronization
	- Requires two app instances at different edge clouds
	- To guarantee data consistency, introduce session priority
		- Primary session with read/write permissions
		- Secondary session with read-only
			- Only rendering
- UEs can be connected to multiple edge clouds simultaneously
	- Both will render and stream (one is primary session, other is secondary)
	- Primary
		- Stream will be displayed
		- Control flow will be sent to this one
	- Stream switch phase
		- Primary and secondary roles switched
		- Compressed freezing

### System Architecture

- Streaming client components:
	- Video streaming
	- User input capture
	- Video decoder
	- Input encoder
- UE migration agent communicates with core network and edge clouds
- Stream selector chooses video streams
- Edge migration agent deployed on edge clouds

### Workflow

1. *Migration initialization*.
	- Triggered when QoS becomes unacceptable
	- UE sends migration request to migration manager of core network
	- Migration manager chooses destination
- 2. *Session Setup*.
	- Migration manager informs migration agent to start session setup
		1. set up 5G communication between UE and destination
			 - trigger PDU session setup procedure
			 - set up GPRS tunneling protocol user plane tunnel
		2. Set up state synchronization session
			- first session is primary
- 3. *State synchronization*.
	- being to synchronize states
- 4. *Dual video streaming*.
	- After edge gets synchronized server starts to capture the video
- 5. *Stream switch*.
	- UE switches roles of edge clouds
	- Main role of downtime for user
	- Can lead to freezing or frame flickers
		- Smooth switching introduced to combat this
			1. SSIM threshold to start the switch
			2. Frame sliding to avoid abrupt signal changes
			3. Asynchronous one-frame buffer to avoid accumulating frame diffs
- 6. *Delayed release*.
	- Start a countdown timer once switch is finished
	- Secondary stream will be released once it ends
		- To combat ping-pong effect
			- Is, when migration triggered often because latency jitters right around threshold

## System Implementation

Three parts:

- 5G network support system
- Streaming system
- Control system

## Evaluation

- Only evaluate performance of VM migration using CSM

- Downtime:
	- VM: ~64ms
	- VM with CSM: ~12ms
- Migration time:
	- VM:
		- most time in pre-copy
		- 78s and 298s for the games
	- CSM:
		- most time from waiting for destination node to start game
		- 2.5s and 4.6s for the games
- Overhead:
	- CPU utilization: CSM has higher overhead per unit of time
	- Memory usage: CSM lower memory usage because no p2p copy

QoE: 4.35% of volunteers reported frame flickers

## Hypotheses

The paper triggers service migration reactively, based on unpredictable client mobility. This assumption doesn't hold in LEO satellite networks since the orbital trajectories of said satellites is highly predictable. This could lead to unnecessary service migrations, thus wasting computational resources and potentially leading to missed connection windows.

*Hypothesis 1*. The migration initialization causes unnecessary service migrations or handover timeouts when applied to LEO satellite constellations since it is triggered based on unacceptable QoS metrics. Instead, service migration can be deterministically scheduled based on satellite mobility.

The paper proposes a dual-rendering mechanism to eliminate the service migration bottleneck of peer-to-peer memory state copy. This is done by synchronizing the states of source and destination servers using the cloud-based logic server which starts the synchronization by sending a snapshot to the destination server. The server with primary session will update state in the cloud-based logic server, all state changes are sent from the logic server to the edge nodes. These state changes are then used to indirectly synchronize source and destination server states.

NOTE: There are two aspects in which I suspect this approach might fail in OEC context:

- Centralized cloud logic server as source of truth
	- Might introduce additional latency when communicating with LEO satellite servers
- Synchronization of servers over time
	- Additional propagation delays might cause the states to never converge during connection window
	
The paper assumes that the latency of the edge-to-cloud communication is negligible enough to allow real-time state synchronization. For live migration in OEC, this assumption does not hold because routing user inputs through a multi-hop path (Ground $\rightarrow$ Satellite $\rightarrow$ Central Cloud $\rightarrow$ Satellite) exceeds the strict latency requirements of real-time rendering ($\le 15$ms). This will presumably cause substantial input lag, breaking the real-time interaction loop during the dual-rendering phase.

Hypothesis 2. Terrestrial cloud-assisted service migration (CSM) methods fail in orbit because the multi-hop propagation delay between terrestrial logic servers and satellite nodes exceeds the interactive latency threshold required for real-time rendering.

*Hypothesis 3*. Prolonged synchronization of source and destination server states can fail in orbit because of time-limited connection window between satellites.
